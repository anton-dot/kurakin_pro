Branch by Abstraction: заменяйте реализацию, не замораживая продукт

Новая реализация пишется месяцами в отдельной ветке, а продукт всё это время меняется. Как перейти постепенно и не накопить огромный риск слияния?

Команда решила заменить библиотеку расчёта цен. Для новой версии открыли отдельную ветку. Через месяц основной продукт ушёл вперёд, через два появились конфликтующие изменения, а через три стало непонятно, сколько ещё займёт слияние. Сам расчёт может оказаться правильным, но цена его доставки выросла задолго до релиза.

Branch by Abstraction предлагает разделить потребителей кода и конкретную реализацию через одну устойчивую границу. Новую реализацию можно готовить в основной линии разработки и включать постепенно, не пряча весь проект в долгоживущей ветке.

Сначала граница, потом переписывание

Условно в системе есть модуль расчёта цены, который вызывают оформление заказа, корзина и поддержка. Вместо прямых вызовов старой реализации вводится интерфейс с понятными бизнес-операциями. Все потребители постепенно начинают обращаться к нему.

Пока граница устанавливается, поведение не должно измениться. Только после этого за интерфейсом появляется новый компонент. Затем для выбранных сценариев можно переключать выполнение между двумя реализациями и сравнивать результаты.

Не стоит просто копировать в интерфейс десятки методов устаревшей библиотеки. Если абстракция повторит все её случайные детали, новая реализация будет навсегда связана старыми решениями.

Проверяйте различия до переключения

Для чистых вычислений можно временно запустить оба варианта на одном наборе входных данных и сравнить результат. Но если компонент списывает деньги, отправляет письма или меняет данные партнёра, второе выполнение создаст настоящий побочный эффект. Здесь нужны специально подготовленные безопасные способы проверки.

Важно заранее определить, какие различия допустимы. Например, новая система может иначе округлять стоимость, и это не обязательно ошибка — но бизнес должен понимать и согласовать изменение прежде, чем оно попадёт клиентам.

Когда обратный путь действительно существует

Флаг выбора реализации создаёт ощущение быстрого отката. Однако если новый код изменил формат данных, старая версия может уже не справиться. Поэтому миграцию данных и правила совместимости нужно рассматривать отдельно.

Во время перехода компания оплачивает поддержку двух вариантов и проверки между ними. Выигрыш в том, что основную разработку можно продолжать, а риск не концентрируется в одном многомесячном слиянии.

Уберите временную конструкцию вовремя

У абстракции, созданной только для миграции, должен быть срок жизни. Когда новая реализация прошла проверки и обслуживает нужные сценарии, старую ветку поведения удаляют. Иначе временный переключатель становится постоянной сложностью продукта.

Для внешних бизнес-процессов, которые целиком переносятся между системами, полезно сравнить этот подход со Strangler Pattern. Здесь же мы прежде всего заменяем внутренний компонент, сохраняя регулярную поставку приложения.

Branch by Abstraction стоит применять не ради ещё одного интерфейса, а ради возможности менять важный механизм без паузы в развитии продукта и без ставки на один огромный merge.

Первоначальная идея подробно описана в Branch by Abstraction у Мартина Фаулера.
