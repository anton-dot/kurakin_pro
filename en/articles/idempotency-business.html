Idempotency: Retry the Request, Not the Payment

The customer clicked Pay and got no response. A second click must not create a second charge — and a UUID header alone is not enough.

The customer clicks Pay, waits for a timeout and clicks again. Nobody can tell from that timeout whether the first request failed to reach the server or completed successfully with its response lost. The two situations look identical in the browser.

Idempotency makes repeated delivery of the same operation safe. For payments, the reason is obvious. The same concern applies to bookings, orders, loyalty points and other commands whose effects cannot be multiplied without consequence.

An operation key is a contract

Clients commonly send a durable identifier of intent, often called an idempotency key. A retry using that key is linked to the original operation rather than treated as a new purchase. The service records the result or state and can return it when the same request arrives again.

The scope matters: which user, operation and retention period make a key unique? If the same key arrives with a different amount or payload, rejecting the mismatch is usually safer than silently treating it as the original request.

Two retries can race each other

A naive “if key not found, charge the card” implementation is unsafe. Two requests may check the table simultaneously, both see nothing and both start processing.

The system needs atomic creation of the operation record, a uniqueness constraint or another appropriate concurrency mechanism. Recording states such as processing, completed and failed can let a retry inspect progress without launching a second business effect.

What does returning the same result mean?

Sometimes the original operation is still running. The API may return an in-progress state and allow the client to check it by operation ID. Starting another payment with a fresh key while the first outcome is unknown is dangerous.

Key retention matters too. If deduplication records expire before an old request can be replayed, the system may treat it as new work. Long-lived operations often need an additional business-identity check, not just a short-lived cache.

Idempotency does not cover every external effect

When the application calls a payment provider, its own key does not automatically make the provider's operation safe. The provider's actual API contract, supported idempotency scope and status lookup are part of the design.

HTTP retries are also not identical to duplicate messages from a broker, where a Transactional Inbox may help. The common requirement is not to mistake a retry for a new customer intention.

The customer should not have to know where the network lost a response. One purchase must remain one purchase, however many times they need to click the button.
