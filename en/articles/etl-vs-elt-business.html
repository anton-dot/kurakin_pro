ETL vs ELT: Should Data Be Transformed Before or After Loading?

Refunds reconcile in the payment system but not in the retailer’s report. What should happen before loading, and what evidence must remain available for a recalculation?

An online retailer asks for the true cost of returns. Sales records the order amount, the payment provider records the refund, and the warehouse records when the goods come back. Combining those tables without agreeing on what each row means produces a polished report and a potentially wrong answer.

The data team must decide where to clean and combine the information: before loading it into the analytics environment, or after. That is the practical difference between ETL and ELT. It changes the cost of reprocessing, the treatment of sensitive data and whether the original evidence is still available when someone challenges a number.

Start with the business question, not the pipeline

ETL stands for Extract, Transform, Load. Data is transformed before being loaded into its target analytical environment. ELT stands for Extract, Load, Transform: source information is loaded first and models are built inside the target platform. These are processing sequences, not mutually exclusive product categories. A real architecture can use both.

Consider a partial return from an order containing several items. The customer requests the refund on Monday, the warehouse receives the item on Thursday, and the payment provider transfers the money on Friday. Which date belongs in the monthly report? The answer depends on what the metric is supposed to represent. Neither ETL nor ELT makes that decision.

Define the unit of measurement and the identifiers used to join records before designing the process. A returned item, a refund transaction and an order are not the same thing. Joining at the wrong level can multiply the same refund. A row-count check may still pass, so reconciliation needs concrete transactions and amounts.

Some transformations should happen before loading

Not everything is appropriate for a raw analytics zone. If an original field contains personal information that the analytical workload has no reason to retain, remove or protect it before transferring the data to another environment. Access restrictions and retention requirements apply before a technically convenient copy gets created.

ETL can standardize currencies, verify mandatory identifiers and reject records that cannot be interpreted safely. That helps when the target must never receive certain unprocessed fields. The trade-off is information loss: a faulty transformation may discard a transaction that later turns out to matter. Recovery then depends on whether an authorized source copy exists elsewhere.

A company can keep original records in a restricted source environment while sending approved, transformed facts to a reporting system. That is a legitimate design even if it does not fit neatly into a vendor's preferred ETL-versus-ELT diagram. What matters is knowing who owns each copy and why it exists.

Loading before transforming can preserve options

ELT becomes useful when questions change more quickly than source systems. Today the retailer needs return cost by product category; next month it may investigate delays between warehouse receipt and refund. Keeping appropriate source facts in a governed landing area can avoid requesting another historical extraction from each operational team.

But “load first” does not mean “make everything available to everyone.” The landing zone still needs source identification, extraction times, completeness checks, permissions and a retention policy. Curated models need definitions and tests of their own. The dbt documentation on data tests describes checks such as uniqueness and relationships that can be maintained alongside transformations.

The tests must reflect the meaning of the model. A unique return identifier may prevent a duplicate, but it does not prove that the refund amount is correct. The team still needs reconciliation with the payment source and a policy for manual adjustments. Versioning the transformation matters too: if last month's report changes after a model update, somebody needs to explain why.

A half-loaded period should never look final

Suppose payment data arrives, but the warehouse feed is late. The result can suggest an unexpected surge in losses or a shortage of confirmed returns. Consumers must know when a reporting period is complete. A table that exists is not necessarily a report that is ready.

Reliable reruns need stable identifiers, duplicate handling and explicit rules for corrections. A canceled return should change the prepared result appropriately rather than merely adding another unexplained row. Data freshness also deserves its own check. dbt's source freshness guidance distinguishes freshness monitoring from whether every downstream calculation succeeded.

If source data is unreliable, moving transformations into a more powerful warehouse only produces unreliable numbers faster. Before adding capacity, identify recurring causes: incompatible identifiers, unapproved corrections or ambiguous event dates.

Compare the complete operating cost

ETL uses resources before loading and can reduce the volume of target data. ELT uses the analytical platform's compute and often keeps more history available for new models. Costs include repeated processing, data transfer, query execution, storage and the engineering work needed to maintain these processes. A low price per gigabyte is not a complete comparison.

There is also portability. A complex transformation implemented entirely in one analytical engine can be expensive to move elsewhere. That dependency may be perfectly reasonable when the benefits are clear; it should simply be part of the decision rather than dismissed as irrelevant because ELT is fashionable.

For this retailer, run both plausible designs against the same return history. Compare final amounts, time to a trustworthy report, recovery after a failed job, access boundaries and the cost of recalculation. A governed landing zone with ELT may be valuable when many questions are still evolving. A stable, narrowly defined report may be better served by earlier transformation. The winner is the process that produces an explainable number on demand, not the one with the more modern acronym.
