Branch by Abstraction: Replace the Implementation, Not the Product Roadmap

The rewrite has been on a separate branch for months while the product keeps moving. How do you migrate without one enormous merge?

The team decides to replace a pricing library. Work starts on a separate branch. A month later the main product has moved on. After two months the changes conflict. After three, nobody can say how long the final merge will take. The new calculation may be correct, but delivering it has become the risky part.

Branch by Abstraction puts a stable boundary between the callers and the implementation. The new component can be developed along the main line and enabled gradually rather than hiding an entire migration in a long-lived branch.

Introduce the boundary before the replacement

Suppose checkout, cart and support tools all call one pricing module. Replace direct dependencies on its implementation with a small interface expressed in business operations. Move the consumers behind that interface while behaviour is still unchanged.

Only then introduce the new implementation behind the same boundary. Selected flows can gradually use it while other calls continue through the old one. Tests can compare the results.

Do not simply copy dozens of legacy methods into the abstraction. If it preserves every accidental detail of the old library, the new component inherits the very design the team wanted to escape.

Compare behaviour before switching

For pure calculations, the team may safely run old and new implementations on the same inputs and compare outcomes. But a component that charges cards, sends emails or changes a partner's state cannot simply execute twice. Those effects need a safe testing strategy.

Define acceptable differences in advance. A new pricing engine may round amounts differently. That could be a deliberate product change rather than a defect, but the business must understand it before customers do.

A switch is not always a rollback

Selecting the old implementation with a flag feels reversible. Yet if the new component has written a changed data format, the old one may no longer understand it. Data migration and compatibility must be designed separately.

There is a temporary cost to running both implementations and comparing them. The benefit is that product development can continue without storing months of change risk in one merge.

Retire the transition machinery

An abstraction introduced solely for migration needs an end condition. Once the new implementation has been validated, remove the old branch of behaviour. Otherwise an intentionally temporary switch becomes permanent complexity.

For complete business journeys moving between separate systems, compare this technique with the Strangler Pattern. Here the goal is primarily to change an internal component while keeping the application releasable.

Branch by Abstraction is not valuable because another interface exists. It is valuable because a critical implementation can change without freezing product delivery or betting everything on a massive merge.
