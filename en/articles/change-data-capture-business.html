Change Data Capture: How to Move Database Changes Without Making Applications Write Twice

An order changes, but search still shows its earlier status. CDC delivers updates; snapshots, replays and recovery determine whether consumers get the right result.

A customer places an order. The transactional database shows it as confirmed, while search in the customer portal still displays the previous state. Analytics, CRM and notifications all want to know that the order changed, but none of them should take part in the transaction that accepted it.

Change Data Capture, or CDC, provides a way to deliver changes already committed to the database. Instead of requiring application code to save the order, update the search index and notify several other systems as one improvised sequence, the database change becomes a separate source of updates. That simplifies one part of the design, but reliable delivery and correct interpretation remain separate responsibilities.

A row change is not necessarily a business event

A CDC implementation may read the database transaction log or another supported change feed. For example, Debezium's PostgreSQL connector uses logical replication and supports an initial snapshot. The exact operations, fields and ordering guarantees depend on the source database and connector configuration.

An update to an order row is not automatically the same as “the order was approved.” One transaction may change several technical records, and an order status may be adjusted for internal processing. A downstream system that does not understand the source model can draw the wrong business conclusion from an accurately captured database update.

Where consumers need explicit business events, the application can write an outbox record in the same transaction as its business change. Debezium's Outbox Event Router illustrates how such records can be published. This is different from pretending every low-level table update carries an agreed business meaning.

The initial snapshot must meet the stream

A new search index cannot start from future changes alone. It needs the existing orders as well. Typically the team initializes from a snapshot and then applies the stream of later changes. The boundary matters: an order updated while the snapshot is being read must not remain in the index with yesterday's status.

The implementation needs a consistent snapshot strategy, a log position, handling for repeated deliveries and a way to reject older updates. A naive “last message received wins” rule may allow a replayed old event to overwrite newer search state. Source version or position information can help when it is available and interpreted consistently.

Deletes require equal care. A row that disappears from a later snapshot is not the same operational mechanism as an explicit deletion event. Test the path the system actually uses, including the removal of data that should no longer be available to the consumer. Publishing data into another index also creates its own access and retention obligations.

Ordering and retries have limits

“Events are ordered” needs a scope: one key, partition, table or stream? Payment and order records may be delivered through separate paths even when they changed together. The consumer needs to tolerate temporarily incomplete information instead of assuming every related fact arrives in one transaction.

After failure or restart, an event may be processed again. Updating a search document should therefore be idempotent: the same source change does not create a second document or send a second notification. If a consumer triggers an external effect, that effect needs its own duplicate protection. CDC does not grant exactly-once business behavior by itself.

Continuous log reading does not mean instantaneous consistency. There is time spent in the source, connector, transport and indexer. For a customer, the relevant measure is when the updated order becomes visible and what the portal does during the delay.

The transaction log is not unlimited storage

Databases do not retain every change forever. A consumer stopped for too long may lose its required position. In other configurations, a stalled replication process can prevent log cleanup and increase pressure on the source. Both cases require monitoring, limits and an explicit recovery procedure.

Measure lag, last processed position, errors and the ability to rebuild. “Connector running” is not a sufficient health check. Following recovery, the search index should converge with the source, not merely resume accepting new events while silently leaving a gap behind.

Schema changes matter as well. A renamed column, different identifier type or split table can break downstream consumers. The feed needs compatibility rules, tests and an identified owner. A restricted database connection also does not mean every downstream subscriber may receive all its contents.

Keep the source of truth explicit

Search may maintain its own copy of order states for fast reading. That does not authorize it to modify orders based on a search result. One business operation still needs a clear owner, or replication gradually turns into several competing authorities over the same fact.

A useful pilot is to create an index, change and delete an order during its initial load, interrupt delivery and then recover. Compare the full state with the source, including a realistic lag and failure of the search service. Search may temporarily be behind; accepting an order must not lose its committed state because an index is unavailable.

For one small periodic report, CDC may be unnecessary. A scheduled extract with an agreed freshness target is often simpler. CDC becomes worthwhile when multiple consumers genuinely require ongoing changes and the organization is prepared to operate the feed: recovering gaps, controlling data access and taking responsibility for the consumer's final result.
