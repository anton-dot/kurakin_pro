Feature Flags: The Code Is Deployed, but the Feature Is Not Launched

A new feature is live in production, but only employees can see it. How to control launch risk without keeping forgotten switches forever.

The team has finished a new delivery-price calculation. Its code is tested and already running in production. Marketing wants a Monday launch; support wants to check real orders first; engineering does not want another deployment every time the audience changes.

A feature flag separates deployment from exposure. The business can turn on behaviour when it is ready, without waiting for another code release. But the convenience adds another system state that somebody will have to maintain.

Not every flag serves the same purpose

A temporary release flag hides work while it is validated. An experiment flag sends defined user cohorts through different behaviour. An operational kill switch disables expensive nonessential functionality under stress. Long-lived permissions tied to subscription plans belong to product access rules rather than release management.

These switches have different owners, lifetimes and change policies. Put everything into one anonymous list of on/off settings and soon nobody remembers who approved what.

A gradual rollout is not about the percentage

Suppose a new payment flow is enabled for a small customer cohort. The plan needs to define how membership is assigned and whether the same user stays in the same cohort across requests. Otherwise someone may start checkout under one implementation and finish it under another.

Choose the measurements in advance: completed payments, refunds, errors, support requests and latency. Widen exposure because the result holds up, not simply because another hour has passed.

And turning off a flag is not always a rollback. If the new flow has already written data or triggered irreversible actions, the old code may no longer understand that state. Test the return path before trusting the kill switch.

Every forgotten flag becomes a maintenance bill

Old and new paths coexist while a flag remains. Both need testing, and combinations become harder to reason about as flags accumulate, especially when features depend on one another.

I would give every temporary flag an owner, a purpose, a review date and a removal condition. When rollout is complete, remove the flag and the unused path. Keeping both forever is paying for last year's launch every day.

When a normal release is simpler

A small, easily reversible change with no need for staged exposure may not justify a flag. Nor should frontend flags be mistaken for access control: the service performing a privileged action still needs to enforce permissions.

I would also distinguish feature rollout from canary deployment. One changes runtime behaviour; the other changes which application version serves traffic. Sometimes the product only needs one.

Feature flags earn their place by removing a measurable risk or a release-coordination delay. A flag with no removal plan is technical debt before the feature has even launched.
