Expand–Contract: Change Data While Old Code Is Still Running

An old approval flag only knew yes or no. New rules need pending, suspended and rejected states. How can the data model change without breaking older clients?

The company is changing how suppliers are approved. The old system stored one flag: approved or not. The new workflow distinguishes pending review, active approval, temporary suspension and final rejection. The richer model makes sense to the business. Unfortunately, older applications still read the original flag and can change it.

Renaming the column is the easy part of the drawing. In production, that can break an older screen, a nightly export and a delayed background job at the same time. Expand–Contract is a staged way to change the contract while older consumers continue working. Its hardest part is not adding a field. It is deciding what happens while two versions of the same business decision coexist.

Find the meaning the old field cannot express

First define what every new state means. Pending and suspended may both map to false, but they should not necessarily trigger identical behaviour. One supplier has never been approved. Another may have existing orders and obligations despite a temporary restriction. Treating them as the same everywhere is risky. Mapping suspension to true can be worse.

Before changing storage, decide what an older consumer may do with a state it cannot represent. Should it display a limited view? Reject a write? Sometimes an explicit refusal is safer than silently converting the new state to the nearest old value.

Look beyond public API clients. Scheduled reports, imports, recovery scripts and direct table readers can preserve an old dependency for much longer than expected.

Expand: introduce the new representation without removing the old one

The first step is additive. Introduce the new field and make application code capable of reading both representations. While older instances still run, the new field may need to remain nullable. A strict not-null constraint comes later, after historical rows are migrated and all relevant writers populate it.

There must be one authoritative interpretation of a state change. If the old program writes approved and the new one writes approval_state independently, the values can diverge. Agree on the component that owns the business decision and how that decision is reflected in both representations. A controlled write path or temporary adapter may help. Two uncoordinated writes are not automatically a transaction.

Test mixed versions, not just the latest release: an old reader seeing a new state, a new reader receiving an old record, or a delayed command sent by an outdated client. Each combination needs an expected outcome.

Backfill must not overwrite a newer decision

Historical values may need to be converted in small, monitored batches rather than through one large update that competes with production traffic. GitLab's batched background migration guidance describes operational limits, idempotent jobs and checks before moving to later changes.

The real danger is a concurrent update. A migration reads approved=true. While it is preparing to write active, an employee suspends the supplier through the new system. If the backfill blindly writes its old value, the suspension disappears. A version check, conditional write or another concurrency control must prevent historical work from replacing a newer decision.

The migration also needs to be resumable. A failed batch should not damage records that were already converted. Track unmigrated rows, failures, data discrepancies and the load caused by the process. A job being scheduled is not evidence that the migration finished.

Some missing information cannot be reconstructed from the old boolean. A previous false may mean under review or permanently rejected. Those records need a deliberate unknown state, another source or a manual business decision. Inventing a confident historical status is not a migration strategy.

Switching reads and stopping old writes are different milestones

Once the new representation is populated, read traffic can gradually move to it. Compare actual business outcomes: approval for a new order, a restriction on a purchase, or the handling of an existing obligation. A perfect row count is not enough if those decisions differ.

Retire writes to the old field only after the consumers that require it have moved. Check infrequent paths too: disaster recovery jobs, monthly reports and devices that reconnect after long periods offline. One quiet day of logs does not establish that the old contract has no users.

Rollback boundaries matter here. An older application may not understand states created after the switch. Amazon Builders' Library describes why rollback-safe changes need careful compatibility design. Restoring an old binary does not undo the new data it already wrote.

Contract only after the old representation has no remaining job

Finally remove the legacy reads, writes, mapping code and old column. Before that deletion, verify that the backfill has completed, old consumers are gone and incorrectly converted records can be identified and repaired. Keeping both representations forever also has a cost: every future state change must be explained to two generations of code.

For supplier approvals, the acceptance test is concrete. A supplier's state has one clear meaning. An outdated client cannot mistakenly authorise a purchase. Historical records remain explainable. Nightly jobs no longer write the old flag. Until those conditions are demonstrated, Contract is still an unfinished task.
